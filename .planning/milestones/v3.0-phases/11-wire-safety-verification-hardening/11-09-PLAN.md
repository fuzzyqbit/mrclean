<objective>
Fix two independent, environment-only test/CI defects surfaced by the first
ubuntu CI run of this branch (`.planning/debug/ubuntu-ci-doctor-exit-5.md`,
diagnosed 2026-07-18) — neither is a product bug; all 8 real linux doctor
checks passed on the same run, and all 3 canary-leak unit suites were green
in the raw log.

(A) `.github/workflows/canary-leak.yml`'s `run_and_guard` count-guard greps
captured vitest output for `Test Files N passed`, but under
`GITHUB_ACTIONS`, vitest colorizes its output with ANSI escape codes that sit
between "Test Files" and "N passed", so the regex never matches — CI reports
false-red even though every collected test passed and the integration pair
never even ran (the script exits before reaching it).

(B) `tests/doctor/end-to-end.test.ts` Tests 1 and 5 call `computeDoctorReport()`
in-process without stubbing `MRCLEAN_TEST_FAKE_CLAUDE_VERSION` (only Test 8
does). On a runner with no real `claude` binary on PATH (every ubuntu CI
runner), `checkClaudeCodeVersion` resolves to `not-found`, and
`computeDoctorReport` escalates an otherwise-all-green report from exit 0 to
exit 5 — the tests only ever passed locally because the developer's machine
happens to have Claude Code installed.

Purpose: make the wire-safety CI gate and the doctor hermeticity suite
reliable across environments (ubuntu CI included) without changing any
shipped detection/redaction/restore behavior.

Output: corrected `.github/workflows/canary-leak.yml`, corrected
`tests/doctor/end-to-end.test.ts`, and a small `src/doctor/index.ts` polish
that removes a noisy, misleading stderr crash dump from an already-passing
check.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI runner (ubuntu-latest, ephemeral) ↔ repository security gates | The wire-safety count-guard and doctor hermeticity checks are the last automated signal before a merge; both must produce a reliable, non-spoofable pass/fail regardless of the runner's terminal/color environment or installed tooling |
| doctor process ↔ spawned canary subprocess | `runMcpCanary`/`runHookCanary` spawn a child process using registered bin paths; an empty/unregistered path must never be silently substituted with an unrelated executable (`process.execPath`) as if it were a valid canary target |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-09-01 | Tampering | .github/workflows/canary-leak.yml `run_and_guard` | mitigate | Force non-colorized vitest output with the documented `--no-color` CLI flag before the `grep -Eq "Test Files[[:space:]]+N passed"` count guard, so a CI-forced-color environment cannot cause a false-red (or worse, a silently-skipped integration pair since the script exits early on non-zero status) — the existing `[ "$status" -eq 0 ]` hard exit-code gate is unchanged and remains the primary correctness signal |
| T-11-09-02 | Denial of Service | tests/doctor/end-to-end.test.ts Tests 1 & 5 | mitigate | Stub `MRCLEAN_TEST_FAKE_CLAUDE_VERSION` (mirroring Test 8's existing pattern) so the hermetic suite never depends on a real `claude` binary on the runner's PATH — closes the ubuntu-CI-only exit-5 false-red without touching any shipped detection/redaction code |
| T-11-09-03 | Information Disclosure | src/doctor/index.ts canary bin-path fallback | mitigate (optional polish) | Replace the `hookBinPath/mcpBinPath \|\| process.execPath` fallback with an explicit `SKIP` `CheckResult` when a bin path is unregistered, so doctor never spawns Node against its own binary — no secret data was ever actually disclosed by the old crash dump (it echoed the node binary's own bytes), but the noisy, misleading output degraded the operator's ability to trust real failure signals in doctor/CI output |
</threat_model>
