<objective>
Close the SC4/HOOK-05 fail-open hole: deleting or renaming the mrclean hook bin currently disables all protection silently.

**Root cause (verified against the live Claude Code hooks contract):** A `type: "command"` hook runs in **exec form when `args` is present** — Claude Code resolves `command` as an executable and spawns it directly with `args`, no shell. The current installer writes `command: <node>`, `args: [<bin>, "hook"]`, so when the bin is gone the process fails as exit 1 (module-not-found) or ENOENT. Claude Code **only blocks on exit 2**; every other exit code is a non-blocking error by platform design. mrclean never gets a chance to exit 2, so the tool call proceeds and the canary leaks (live UAT-2b evidence in 01-UAT.md).

**The fix:** the installer writes a fail-closed shell wrapper so ANY inner failure becomes exit 2. POSIX (primary, tested): exec-form `/bin/sh` with the inner invocation passed as **positional parameters** (`"$1" "$2" hook || exit 2`) — sh quotes the paths (injection-safe) and passes stdin straight through to node. Because the wrapper lives in the OS shell (not in the deletable `dist/`), it survives bin deletion and fails closed. win32 is a documented known-gap this plan (no shell wrapper — see design_notes).

Purpose: restore the fail-closed guarantee at the spawn layer without new runtime deps, keeping the hook one exec deep and within the <100 ms budget.
Output: a spawn-failure-proof POSIX hook command shape, doctor realigned to read it, all coupled tests synced, and the stale 01-VERIFICATION.md human items corrected.
</objective>

<design_notes>
## Wrapper contract (buildHookCommand)

`buildHookCommand(nodePath, mrcleanBinPath, platform = process.platform)` returns a `HookCommand`
(`{ type:'command'; command; args; timeout:10 }`). Both platform branches keep `args` present so
the existing `HookCommand.args: string[]` type is unchanged.

- **POSIX (darwin/linux) — primary, deterministically tested:**
  - `command`: `/bin/sh`
  - `args`: `['-c', '"$1" "$2" hook || exit 2', 'mrclean-hook', nodePath, mrcleanBinPath]`
  - Semantics: `$0` = `mrclean-hook` label, `$1` = nodePath, `$2` = mrcleanBinPath. sh quotes the
    positional params (no string interpolation of paths → no shell injection, handles spaces).
    `node bin hook` inherits sh's stdin/stdout/stderr (hook payload still flows in on stdin, and the
    hook's stdout JSON — banner/permissionDecision — flows straight back out). `|| exit 2` fires on
    ANY non-zero inner status (1, 2, 127, signal death) → sh exits 2 (BLOCK). Inner exit 0
    short-circuits `||` → sh exits 0 (PASS). Inner exit 2 (mrclean crash guard) → `|| exit 2` → sh
    exits 2 (BLOCK preserved).

- **win32 — KNOWN GAP (no wrapper this plan; constraint deprioritizes Windows):**
  - `command`: `nodePath`
  - `args`: `[mrcleanBinPath, 'hook']`  (the existing plain exec form — NOT a shell wrapper)
  - Rationale: the cmd.exe nested-quote wrapper (`cmd /d /s /c ""<node>" "<bin>" hook" || exit /b 2`)
    is fragile and untested; a single mis-quote would false-positive BLOCK every tool call for
    Windows users. Rather than ship an untested wrapper, win32 keeps the plain exec form and
    therefore stays fail-OPEN on spawn failure (missing bin) until a tested wrapper ships. Documented
    known-gap; the POSIX branch is the only fail-closed path this plan.

## Why the doctor must change in the same plan
`src/doctor/checks.ts` currently reads the mrclean bin from `cmd.args[0]` (collectRegisteredBinPaths)
and node from `cmd.command` (extractRegisteredPaths). Under the wrapper, `args[0]` is `-c` and
`command` is `/bin/sh`. Extraction must read the **tail** of `args` instead:
`mrcleanBinPath = args[args.length - 1]`, `nodePath = args[args.length - 2]`, with a legacy fallback
(if `args[0]` ends with `.js`, use the old positions) so doctor tolerates both shapes during
migration — and also tolerates the win32 plain-exec shape (which the legacy fallback already matches).

## Migration / idempotency (safe by construction — do not weaken)
`isMrcleanEntry` (src/install/markers.ts) keys on the `_mrclean: true` marker on the ENTRY object,
NOT on the command shape. `writeHookEntries` filters entries by that marker before re-adding, so an
already-installed user's old-shape entries are replaced, not duplicated. `removeHookEntries` strips
by the same marker. Keep the marker on the entry; the wrapper only changes `entry.hooks[0]`.

## Constraints to honor
- Zero new runtime deps (wrapper uses OS `/bin/sh`; test uses `node:child_process`).
- Hot-path budget <100 ms: one extra `sh` exec (~1-3 ms). Current p95 = 17.4 ms — ample headroom.
- Atomic settings.json writes preserved (writeHookEntries already uses atomicWriteJson).
</design_notes>
